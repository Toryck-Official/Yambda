## 一、当前研究主线

当前主线固定为：

数据集清洗
→ 显式反馈 + Item 的 SNMPP 建模
→ 验证 SNMPP 是否学到可靠的反馈-物品时间关系
→ explicit-feedback HPN
→ SNMPP + HPN 融合
→ 调查 SNMPP + HPN + BOLA 的融合方式
→ 次要调查 Reward Constrained Interactive Recommendation with Natural Language Feedback 的历史反馈利用方式
→ 最终 Recall / NDCG / 时间预测 / 反馈预测等完整评估
→ RL/BOLA 只在前面的推荐模型已经成立以后考虑

不是以“把所有模块都跑起来”为成功标准。

每一阶段都必须允许得到：“该假设不成立，因此停止这一分支”。

## 二、已经确认的原则：不要重新讨论

### 原则 1：彻底舍弃 listen

当前工作研究的是显式反馈本身：

- like
- dislike
- unlike
- undislike

listen 不属于主事件。

所有当前主线的数据集、SNMPP 和主 HPN 都采用 explicit-feedback-only 协议。

不要因为以前 listen-based HPN 指标更高，就重新把 listen 加回主模型。

旧 listen HPN 可以保留作为历史参考，但不能与当前主实验混用。

### 原则 2：删除的是 listen 事件，不是包含 listen 的用户

原始日志中，如果一个用户同时有 listen 和显式反馈：删除 listen rows，保留显式反馈。

只有当删除 listen 后该用户已经没有任何显式反馈事件时，这个用户才自然从数据集中消失。

### 原则 3：使用完整 5B sequential 日志进行筛选

目标是下载或定位完整 sequential 数据。

5B 是原始交互规模，不默认等于最终显式反馈事件数量。

必须先统计：

raw interactions
→ remove listen
→ explicit interactions

最后论文和实验中必须明确真实使用了多少显式事件。

### 原则 4：不引入其他推荐数据集

本文聚焦：

music recommendation
+ explicit preference feedback
+ preference revision
+ continuous-time dynamics

不为了“多数据集”而强行增加 MovieLens、Amazon 等数据。

当前工作就是针对音乐场景的特化方法。

### 原则 5：不再使用用户模拟器和 A2C

A2C + simulator 主线彻底放弃。

原因不是工程实现失败，而是：

Yambda 不具备完整曝光后 accept/reject 日志，模拟器无法可靠模拟完整推荐环境，而模型驱动 RL 又会引入额外模型误差。

当前不要继续：

- user simulator
- A2C
- model-based RL rollout

BOLA 是后续独立研究问题，不等价于重新恢复旧 A2C。

### 原则 6：当前研究对象是“下一显式反馈事件”

我们希望模型看到：

`H_t = 用户在时间 t 之前的显式反馈历史`

然后预测下一次真实发生的显式事件：

`e_(n+1) = (feedback type, item, time)`

因此模型最终不能只回答“下一次更可能发生 like”。

我们希望进一步回答：“下一次更可能对哪一首歌发生什么反馈，并且大概什么时候发生”。

### 原则 7：Feedback type 与 Item 不建立联合百万级 ID

四种反馈仍然只有四种反馈类型：

- 0 = like
- 1 = dislike
- 2 = unlike
- 3 = undislike

一个 feedback type 对应一个 event embedding。

禁止创建 like-item-A、like-item-B、like-item-C 等 feedback × item 联合 event vocabulary。

Item 信息通过 SID representation 进入事件表示。

### 原则 8：只编码真正出现在显式反馈数据中的歌曲

首先从完整日志删除 listen。

定义 `I_explicit` 为所有至少出现在一次 like/dislike/unlike/undislike 事件中的 item 集合。

当前主实验只需要为 `I_explicit` 中的歌曲建立或保留 SID 编码。

不要为了整个 Yambda catalog 中只出现 listen、从未出现显式反馈的歌曲建立当前主模型 vocabulary。

必须报告：

- 原始 catalog item 数
- explicit-feedback item 数
- explicit item coverage
- SID coverage

最终论文必须明确：这是 explicit-feedback item universe，不能描述成完整音乐库 full-catalog recommendation。

### 原则 9：SID codebook 冻结

现有 RQKMeans/Semantic ID codebook vectors 必须冻结。

不允许在 SNMPP 训练过程中更新 codebook。

如果需要额外 projection，例如 512 → 64，projection layer 可以训练，但原始 codebook vector 必须满足 `requires_grad = False`。

### 原则 10：严格时间顺序，无未来信息泄漏

所有模型输入必须只使用目标事件发生以前的历史。

如果存在同 timestamp 多事件，不能人为为同时间戳事件创造不存在的顺序。

需要采用 event group/shared pre-group history 的方式处理。

train/validation/test 必须采用 global chronological split。

### 原则 11：主验证目标必须包含完整“反馈 + Item”预测

不能只看 NLL 或 feedback type accuracy。

最严格指标必须验证模型预测出的下一 `(feedback type + item)` 是否与日志真实下一事件完全一致。

同时由于 SID 是层级语义表示，必须加入更宽松的 coarse-to-fine 预测指标，判断模型是否至少预测到了正确的歌曲语义区域。

### 原则 12：不要为了提高指标改变协议

如果结果不好，先汇报结果和原因。

不要自行：

- 改 split
- 删除困难样本
- 改候选集
- 改事件定义
- 加 listen
- 改评价指标
- 加额外数据

任何 protocol change 必须先向用户说明。

## Phase 3：SNMPP 第一版——按当前想法建模事件

这一步按照当前方案优先实现，不要先替换成其他 factorization。

历史中的每一个事件同时包含：feedback + item semantic representation + timestamp。

Feedback 部分使用四种 feedback type。

使用一个可学习 embedding table：`event_embedding: 4 × d_event`。

首先确认原 SNMPP 使用的 embedding dimension。第一版优先使用原论文设置。

随后可以测试 `d_event = 4/8/16`，但不要先做大规模 sweep。

### 方案 A：Full Vector Event Representation

假设当前 SID 有四层 semantic code，每层对应一个冻结的 128 维 codebook vector：`c1, c2, c3, c4`。

构造：

`item_vector = concat(c1, c2, c3, c4)`

维度为 `4 × 128 = 512`。

事件表示：

`z_n = concat(feedback_embedding, item_vector)`

即约为 `d_event + 512`。

codebook vector 全部冻结。

第一版优先直接按照这个表示训练。

如果发现计算量明显过大，可以额外测试 `512 → trainable projection → 64/128`，但这是优化方案，不要直接取代原始 full-vector experiment。

## Phase 7：首先研究 SNMPP + HPN 怎么融合

这一阶段不要直接上 BOLA。

先回答 SNMPP 学到的 feedback dynamics + item-aware temporal information 如何帮助 HPN 进行 next explicit-feedback item prediction。

首先提出多个候选融合方案，但不要一次全部实现。

优先研究：

### 方案 1：State-level fusion

将 SNMPP 学到的动态状态注入 HPN history representation。

### 方案 2：Candidate reranking

HPN 先产生候选 item。SNMPP 根据当前历史和 candidate item，计算与未来显式反馈有关的 score，再重新排序。

### 方案 3：Joint training

共享 feedback/item representation，同时优化 SNMPP temporal objective + HPN hierarchical next-item objective。

### 方案 4：History weighting

利用 SNMPP 的 feedback relation/temporal kernel，给历史显式反馈事件赋不同权重，再供 HPN 编码。

例如近期 dislike、长期 like、like 后出现 unlike，可能对当前 user representation 贡献不同。

先分析每种方案：

- 输入是什么
- 输出是什么
- 是否需要 candidate-conditioned SNMPP
- 是否产生数据泄漏
- 参数量
- 训练复杂度
- 能否明确提升 Recall/NDCG

然后向用户汇报，由用户决定先实现哪一种。不要自行全部实现。

## Phase 11：最终评估框架
