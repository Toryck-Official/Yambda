# Phase 1 清洗与分组实施契约

日期：2026-08-10

状态：实现方案。尚未物化 canonical dataset，尚未删除任何事件。

## 1. 输入与守恒基线

输入为 Phase 0 审计的完整 5B sequential 日志中的四类显式反馈：

```text
like
dislike
unlike
undislike
```

Phase 0 基线：

| 统计 | 数量 |
|---|---:|
| explicit events | 136,292,476 |
| explicit users | 857,499 |
| explicit items | 2,875,071 |
| like | 89,334,605 |
| dislike | 11,579,143 |
| unlike | 32,944,520 |
| undislike | 2,434,208 |
| exact duplicate surplus | 1,213,728 |

只删除 exact duplicate surplus 后，预期事件行数为 135,078,748。该数字必须由实际输出重新守恒验证，不能只按减法写入 manifest。

## 2. 唯一确定性删除规则

主键完全相同的 `(uid,item_id,timestamp,feedback_type)` 记录只保留一条。

Canonical retained row 同时保存：

```text
source_duplicate_multiplicity
is_exact_duplicate_removed_source
```

其中 `source_duplicate_multiplicity >= 1`；当原始副本数大于 1 时，`is_exact_duplicate_removed_source=true`。被删除的 surplus 不再单独作为事件，但 cleaning audit 必须统计：

- rows before/after；
- surplus 总数和四类反馈分布；
- affected users；
- affected items；
- affected timestamp groups。

## 3. Group 定义

同一 `(uid,timestamp)` 的全部事件属于一个 timestamp group。建议无碰撞、可逆地定义：

```text
group_id = (uint64(uid) << 32) | uint64(timestamp)
```

同时保留原始 `uid` 和 `timestamp`，不能只保存哈希值。

建议增加：

```text
timestamp_group_size_after_dedup
is_multi_event_timestamp_group
has_same_timestamp_multi_feedback
```

`has_same_timestamp_multi_feedback` 明确定义为：同一个 `(uid,item_id,timestamp)` 在去重后仍包含两个或以上不同 feedback type。它表示 within-group ordering ambiguity，不表示业务冲突。

## 4. Shared pre-group history

对用户按 timestamp 严格递增处理。设当前 group 为 `G_j`：

1. 先使用此前已结束 groups 构造 `H_{t_j^-}`；
2. `G_j` 中所有事件共享完全相同的 `H_{t_j^-}`；
3. 不把 `G_j` 中任何事件用于预测同组另一事件；
4. 整个 `G_j` 处理结束后，再把它作为一个无内部顺序的 event set 加入后续 history。

Canonical event table 可一行一个事件，但 dataloader 必须按 group 读取。仅把相同 group_id 写在行上、训练时仍逐行更新 history，不符合协议。

## 5. 状态审计标签

以下情况全部保留，只增加标签：

```text
repeated_like
repeated_dislike
like_while_disliked
dislike_while_liked
unlike_without_observed_active_like
undislike_without_observed_active_dislike
ambiguous_same_item_time
```

建议将 `state_anomaly_flag` 实现为可解释 bitmask，并在 manifest 中保存每一 bit 的名称。该字段只是审计特征，不能默认作为删除条件。

同一个 `(uid,item,timestamp)` 有多个反馈时，不在组内推断状态顺序，也不把该组配成 strict revision。它对后续状态的影响记为 ambiguous；不能任意挑一个反馈作为最终状态。

## 6. Revision 标签和严格子集

主数据中的 unlike/undislike 无论能否匹配前序原反馈都保留。

```text
left_censored_revision=true
```

表示当前观测窗口内无法形成无歧义 strict pair；它既可能是左删失，也可能是真正 unmatched，标签本身不声称二者可区分。

严格 revision 子集要求：

- same uid；
- same item；
- like 严格早于 unlike，或 dislike 严格早于 undislike；
- 两端均不属于 same-item same-time ambiguity；
- 当前 active original 尚未被对应 revision 解除；
- 不跨同 timestamp 推断顺序。

Strict pair table 建议保存 origin_group_id、revision_group_id 和 delay_seconds；它是分析表，不筛选主事件表。

## 7. Burst 标记和数据版本

全量分布审计完成前不定义 batch_event_flag 阈值。

确认阈值 `T` 后：

```text
batch_event_flag = timestamp_group_size_after_dedup > T
```

同时准备：

- `D_all`：不因 burst 删除事件；
- `D_human_like`：只排除 `batch_event_flag=true` 的完整 groups。

不能从 burst group 中只删部分事件。阈值敏感性必须报告影响的 groups、events、users、feedback composition 和 strict revision pairs。

当前主实验使用哪个版本，必须在全量审计后由用户确认。

## 8. Global chronological split

Split 依据全局 timestamp，而不是每用户分别切分。边界 timestamp 上的所有用户 groups 必须整体进入同一 split，防止相同真实时刻被人为切开。

建议流程：

1. 在 group-level event count 分布上寻找目标比例附近的两个 timestamp；
2. 将 timestamp 小于等于第一边界的所有 groups 放入 train；
3. 中间 timestamp groups 放入 validation；
4. 晚于第二边界的 groups 放入 test；
5. 报告实际 events/users/items 比例，而不是只报告目标比例。

当前协议没有明确指定 80/10/10 或其他比例，因此不得擅自物化 split。需要用户确认目标比例后执行。

SID 重建尚未完成时，可以先生成不含 SID 的 deduplicated event staging，但不能把 staging 冒充最终 canonical dataset。


最终至少验证：

- group_id 对 `(uid,timestamp)` 一一对应；
- 同一 group 不跨 split；
- 所有 item 属于 2,875,071 explicit item universe；
- SID mapping 覆盖全部 explicit item；
- shared pre-group history 单元测试通过。

## 11. 当前未决且禁止擅自决定的事项

2. global chronological split 的目标比例；
