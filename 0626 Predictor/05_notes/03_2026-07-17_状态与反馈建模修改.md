完整方法设计仍以以下文档为主：

## 2. 本次修改的直接原因

修改前存在四个主要问题：

1. Predictor 自己从原始事件构造时间步，与 `Regret` 已有的会话和连续同物品聚合口径不完全一致。
2. 状态主要依赖固定历史序列，没有明确区分当前会话短期偏好和先前会话长期偏好。
3. 播放完成度在目标设计中过重，四类显式反馈没有被当作主要预测对象。
4. 多步回报、真实下一状态和数据切分边界之间缺少严格约束，可能产生训练目标跨越验证或测试时间步的问题。

本次修改的核心决定是：

```text
主要预测目标：候选物品条件下的五维反馈概率
辅助预测目标：播放完成度、v2 即时奖励、后悔类型
状态来源：当前决策前已经发生的用户历史
在线未来信息：只能由 Predictor 根据当前状态和候选物品预测
```

## 3. 推荐时间步定义

### 3.1 不再把单条原始事件直接当作推荐时间步

预处理现在调用：

```text
Regret/scripts/02_split_transitions.py
```

并固定使用：

```text
trajectory_mode = session_run
reward_version = v2
```

处理顺序是：

```text
用户原始事件
-> 按时间间隔和最大会话长度切分 session
-> 在同一 session 内聚合连续出现的相同 item
-> 每个连续 item run 形成一个推荐时间步
```

例如原始记录为：

```text
歌曲 A：listen，播放 80%
歌曲 A：like
歌曲 B：listen，播放 20%
```

现在构造两个时间步：

```text
时间步 1：item=A，listen=1，like=1，播放完成度=0.8
时间步 2：item=B，listen=1，播放完成度=0.2
```

这里的系统动作仍然是“推荐哪个 item”。`listen`、`like`、`dislike`、`unlike`、`undislike` 都是该动作之后观察到的用户响应，不是五种推荐动作。

### 3.2 聚合为什么不构成状态泄漏

对时间步 `t` 预测反馈时：

```text
输入：时间步 t 之前的历史 + 当前候选 item
标签：当前 item 响应窗口内真实发生的反馈
```

当前响应窗口里的反馈不会进入 `s_t`。只有到下一个决策时间步时，这些已经发生的响应才进入历史状态。

因此，聚合窗口中的 `listen + like` 可以共同作为当前动作的监督标签，但不能提前作为当前动作的输入。

### 3.3 仍然存在的动作归因限制

Yambda 数据中没有明确的 `recommend` 曝光字段。当前时间步只能依据可见交互序列近似还原，不能证明每个 item run 都对应一次平台主动推荐。

尤其是延迟发生的 `unlike` 或 `undislike`，如果中间已经出现其他物品，它可能形成新的 item run。工程上能够保留该反馈，但其与原推荐动作之间的因果归因仍然有限。

因此论文中应表述为：

```text
根据可观测交互序列构造的离线推荐时间步
```

不应表述为：

```text
数据提供了完整且无歧义的推荐曝光日志
```

## 4. 当前状态定义

### 4.1 状态不是单独保存的固定向量

原始状态由决策时已经观察到的历史字段组成，经过共享 `StateEncoder` 动态编码后才成为 `state_emb`。

当前逐时间步输入包括：

```text
历史 item embedding
历史五维反馈向量
历史播放完成度
播放超过 100% 的额外部分
历史交互是否为 organic
相邻时间步的时间间隔
历史位置是否属于当前 session
序列位置
padding mask
```

代码位置：

```text
0626 Predictor/02_model/state_encoder.py
```

### 4.2 五维历史反馈向量

每个历史物品位置使用：

```text
[listen, like, dislike, unlike, undislike]
```

这五个值不是互斥类别。例如：

```text
[1, 1, 0, 0, 0]
```

表示该物品响应窗口中既发生了播放，也发生了点赞。

### 4.3 播放信息

播放信息被拆成两个连续值：

```text
play_ratio：原始播放完成度
play_excess：max(play_ratio - 1, 0)
```

例如：

```text
播放 80%：play_ratio=0.8，play_excess=0
播放 130%：play_ratio=1.3，play_excess=0.3
```

这样不会在状态输入阶段丢掉超过 100% 的回拉或重复播放信息。

### 4.4 短期与长期状态

共享状态编码器产生三部分表示：

```text
full_state：按时间顺序编码后的完整历史状态
short_state：历史窗口内属于当前 session 的位置池化
long_state：历史窗口内属于先前 session 的位置池化
```

最终状态为：

```text
state_emb = Fusion(full_state, short_state, long_state)
```

这种做法不会破坏原有 session 切分，因为数据中保留：

```text
user_id
session_id
session_step_idx
user_step_idx
history_same_session
```

### 4.5 当前长期状态的严格含义

当前 `long_state` 不是用户完整终身画像。它只池化最近 `history_len` 个时间步中属于先前 session 的部分。

默认：

```text
history_len = 50
```

如果当前 session 已经占满 50 个位置，那么窗口里没有先前 session，`long_state` 会退化为零向量。

这是当前实现的明确限制。后续如需用户级长期记忆，必须按时间前缀逐步更新，不能先使用该用户完整日志池化，再回头构造训练样本，否则验证和测试行为会进入训练状态。

## 5. 反馈预测目标

### 5.1 主要输出

Predictor 对每个候选物品 `a` 输出五个独立概率：

```text
P(listen | s_t, a)
P(like | s_t, a)
P(dislike | s_t, a)
P(unlike | s_t, a)
P(undislike | s_t, a)
```

实现使用五个独立的 sigmoid，不使用 softmax。

原因是这些响应可以共同发生，五个概率之和不需要等于 1。

### 5.2 标签采用原始事件发生与否

四类显式反馈标签使用：

```text
has_like
has_dislike
has_unlike
has_undislike
```

不使用：

```text
effective_like
effective_dislike
effective_unlike
effective_undislike
```

原因是 `effective_*` 会按照撤销关系调整反馈，适合计算 `v2 reward`，但可能消掉用户真实发生过的反馈事件，不适合作为“反馈分布”的主要监督标签。

例如同一窗口内先 `like` 后 `unlike`：

```text
主反馈标签：like=1，unlike=1
v2 reward：继续按照有效反馈和撤销规则计算
```

这样可以同时保留可解释的真实反馈分布和原有奖励定义。

### 5.3 稀疏反馈类别权重

预处理会统计训练集中五类反馈的正例数：

```text
response_positive_counts
```

训练时根据正负样本比例计算每类正例权重，并默认限制在：

```text
[1, 50]
```

目的不是人为提高显式反馈概率，而是防止大量负例让模型学成“所有显式反馈都预测为 0”。

上限用于避免极少正例产生过大的梯度。正式实验必须把上限作为超参数进行消融，不能默认认为 50 最优。

## 6. 播放、奖励和后悔辅助目标

### 6.1 播放完成度

播放完成度不再是主要目标，只在真实标签满足：

```text
listen = 1
```

时计算回归损失。

对于没有发生播放的样本，不强迫模型把播放完成度回归为 0，因为“未播放”和“播放后立即停止”不是完全相同的含义。

### 6.2 v2 即时奖励

真实奖励继续由 `Regret` 的最新 `v2` 规则生成，不使用 `v1`。

Predictor 使用独立奖励头预测有界即时奖励：

```text
predicted_reward = 2 * tanh(reward_head(hidden))
```

输出范围与默认 `v2 reward` 的裁剪范围一致：

```text
[-2, 2]
```

奖励头是辅助目标。它与反馈头共享状态和候选条件表示，但不会把 `effective_*` 奖励规则强行施加到五个原始反馈概率上。

### 6.3 后悔类型

后悔类型仍然是由播放完成度和有效负反馈派生的辅助标签：

```text
none
low_play
dislike
unlike
```

它不是 Yambda 原始字段，也不是额外的用户动作。

### 6.4 默认损失权重

当前默认值为：

```text
response_loss_weight = 1.0
play_loss_weight = 0.1
reward_loss_weight = 0.1
regret_loss_weight = 0.1
```

因此代码层面已经明确：反馈分布是主要目标，其他三项是辅助约束。

这些权重是初始工程值，不是经过全量验证得到的最优值。

## 7. 下一状态和价值训练

### 7.1 真实下一状态监督

离线数据为每个时间步保存：

```text
history
next_history
```

`next_history` 表示把当前真实 item 和当前真实反馈追加到历史之后得到的前缀。

训练时：

```text
真实 next_history
-> StateEncoder
-> real_next_state_emb
```

Predictor 对日志动作给出反馈概率、播放、奖励和后悔预测，`SoftStateBuilder` 构造：

```text
predicted_next_state_emb
```

使用状态一致性损失：

```text
L_state = MSE(predicted_next_state_emb, real_next_state_emb)
```

这解决了旧实现中 `soft_next_state` 只有名称和前向计算、缺少可靠直接监督的问题。

### 7.2 soft next state 的在线边界

`soft_next_state` 只用于当前候选物品的价值估计：

```text
当前真实状态 + 候选 item + 预测反馈
-> 临时候选下一状态
-> value head
-> 候选未来分数
```

它不会写入用户真实历史。

下一次真实推荐时，系统必须使用用户实际发生的反馈重新构造状态，并重新计算新的候选预测。

### 7.3 价值目标

当前 ValueHead 同时使用三类约束：

```text
一步时序目标
同一数据切分内的多步 future_return
候选集合上的预测后果最大化目标
```

一步目标为：

```text
r_t + gamma * bootstrap_mask * V_target(s_{t+1})
```

候选目标保留多场景采样后的“每个场景先对候选取最大，再对场景平均”的实现。

候选损失默认权重为：

```text
candidate_loss_weight = 0.1
```

它使用缓慢更新的目标价值网络计算候选下一状态价值，减少训练目标和当前 ValueHead 同时快速变化的问题。

## 8. 数据切分与未来信息边界

### 8.1 future return 不跨数据切分

训练样本的 `future_return` 只能累积后续仍属于训练集的时间步。

例如：

```text
train_t -> train_t+1 -> val_t+2
```

训练时间步 `t` 的 future return 最多使用 `train_t+1`，不能读取 `val_t+2` 的真实反馈或奖励。

### 8.2 切分末尾停止自举

如果当前时间步的下一步已经属于其他数据切分：

```text
bootstrap_mask = 0
```

否则：

```text
bootstrap_mask = 1
```

因此训练集末尾不会通过 `V(s_{t+1})` 间接使用验证或测试时间步。

### 8.3 离线与在线允许的信息

离线训练允许：

```text
使用当前动作之后的真实反馈作为监督标签
使用真实 next_history 监督软下一状态
使用同一数据切分内的未来奖励监督 ValueHead
```

在线推荐只允许：

```text
当前已观察历史
当前候选 item
Predictor 根据二者生成的预测反馈和临时下一状态
```

在线禁止：

```text
真实未来反馈
真实 future_return
真实 next_history
验证集或测试集行为形成的用户池化表示
```

## 9. HPN 与 Predictor 的状态一致性

HPN 和 Predictor 现在都调用同一个：

```text
StateEncoder
```

这保证两者对 `s_t` 的字段定义一致。

HPN 的职责仍然是根据当前状态逐层预测 SID，产生候选集合；Predictor 的职责是对每个候选 item 预测可能反馈和后果。Predictor 没有直接替代 HPN 的策略生成。

历史长度也不再在多个训练和评估脚本中静默写死。训练检查点保存 `max_seq_len`，评估和价值训练从检查点恢复相同设置。

## 12. 当前不能过度宣称的内容

### 12.1 小样本指标没有效果意义

本机测试只读取极少用户。样本中绝大多数响应是 `listen`，四类显式反馈正例非常少，不能据此判断模型是否真正学会显式反馈。

### 12.2 不是完整用户终身状态

当前长期状态只覆盖固定历史窗口中的先前 session。要验证它是否足够，服务器需要统计：

```text
每个样本历史长度
当前 session 长度
long_state 有效位置数量
long_state 为空的样本比例
不同 history_len 下的覆盖变化
```

### 12.3 不是完整环境模拟器

Predictor 只预测候选条件下的响应和临时后果表示，没有生成完整可持续交互轨迹，也不会把预测状态永久滚动到下一轮线上推荐。

因此当前更准确的定位是：

```text
基于预测模型的离线强化学习式候选重排
```

而不是：

```text
已经完整实现可无限滚动的用户环境模拟器
```

### 12.4 Bellman-Jensen 定位仍需谨慎

当前已经实现受 Bellman-Jensen 启发的多场景候选最大化目标，但 Predictor 的反馈分布、软状态近似和连续推荐状态与论文中的有限状态转移分布并不完全相同。

论文表述应保留“受其启发”或“工程近似”，不能直接声称完全复现原论文的贝叶斯最优价值函数。

## 13. 服务器下一步必须检查

1. 统计全量 train、val、test 中五类反馈正例和共现矩阵。
2. 统计 `listen + like`、`like + unlike` 等多标签组合的真实数量。
3. 检查显式反馈类别权重是否造成预测概率系统性偏高。
4. 报告每类精确率、召回率、F1 和概率校准，不能只报告总体准确率。
5. 统计长期状态有效覆盖率，并比较 `history_len=50/100/200`。
6. 检查 HPN 候选召回；真实 item 不在候选集时，Predictor 无法通过重排找回。
7. 比较只使用 HPN、加入即时预测、加入 ValueHead 三组结果。
8. 对反馈损失权重、辅助损失权重、候选价值损失权重和 `sample_m` 做消融。
9. 单独报告推理延迟，特别是候选数量增加后的 Predictor 计算成本。
10. 检查 organic 交互作为历史信息和作为目标时间步时的比例及影响。

## 14. 当前结论

本次修改已经把工程口径统一为：

```text
session_run 聚合时间步
+ 当前会话短期状态
+ 历史会话长期状态
+ 候选物品
-> 五维原始反馈概率为主
-> 播放、v2 reward、后悔为辅助
-> 临时预测下一状态
-> ValueHead 和候选重排
```

在线每一步仍然只使用真实历史重新计算状态。Predictor 的输出用于当前候选决策，不替代下一轮真实用户反馈。
