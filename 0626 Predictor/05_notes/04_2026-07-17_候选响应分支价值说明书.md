## 1. 说明书目的

本文统一推荐系统中的以下基础概念：

```text
用户历史
状态
状态表示
推荐动作
候选集合
用户响应
响应分布
即时奖励
下一状态
价值函数
策略
```

核心目的是避免三类混乱：

1. 把系统推荐的物品和用户反馈都叫作“动作”。
2. 把一个反馈期望向量误认为完整的反馈概率分布。
3. 把临时预测下一状态误认为下一轮线上真实状态。

## 2. 一句话定义整个推荐过程

在时间步 `t`：

```text
系统读取用户截至当前已经发生的历史 H_t
-> 编码得到状态表示 z_t
-> 策略网络生成候选物品集合 C_t
-> 对每个候选物品 a 预测用户可能产生的响应分布
-> 对每种可能响应计算即时奖励和分支下一状态价值
-> 汇总成候选价值 Q(z_t, a)
-> 从候选集合中选择最终推荐物品 a_t
-> 用户产生真实响应 y_t
-> 使用真实响应更新历史，形成 H_{t+1}
```

必须区分：

```text
a_t：系统选择的推荐物品
y_t：用户对该推荐物品产生的响应
```

二者不是同一种变量。

## 3. 基础对象与统一符号

### 3.1 用户可观察历史 `H_t`

`H_t` 表示时间步 `t` 做出推荐之前，系统已经观察到的全部可用信息。

可以写成：

```text
H_t = [(a_1, y_1, c_1), (a_2, y_2, c_2), ..., (a_{t-1}, y_{t-1}, c_{t-1})]
```

其中：

```text
a_i：第 i 步交互对应的物品
y_i：用户对该物品的响应
c_i：时间间隔、会话、来源等上下文
```

在当前 Yambda 工程中，历史实际采用最近固定长度的前缀，而不是无限长序列。

默认：

```text
history_len = 50
```

### 3.2 状态 `s_t`

强化学习中的状态 `s_t` 是做出决策所依据的信息集合。

在当前项目中，可以把状态理解为：

```text
s_t = H_t 中用于决策的可观察字段
```

状态不是“用户所有反馈的一个累计分数”。如果只保留一个累计分数，以下两段历史可能被错误地视为相同状态：

```text
历史 A：连续完整播放三首摇滚歌曲
历史 B：完整播放一首摇滚，随后 dislike 两首摇滚
```

即使二者累计奖励恰好相同，用户当前偏好和下一步风险也明显不同。

因此状态必须保留足够的序列、物品和响应信息。

### 3.3 状态表示 `z_t`

原始状态 `s_t` 通常是变长历史，不能直接输入所有决策模块，所以使用编码器得到固定维度表示：

```text
z_t = Encoder(s_t)
```

当前项目中的 `z_t` 对应 `StateEncoder` 输出的：

```text
state_emb
```

它融合：

```text
完整有序历史
当前会话短期偏好
历史窗口内先前会话的长期偏好
```

需要严格区分：

```text
s_t：原始可观察状态
z_t：神经网络编码后的状态向量
```

论文中如果直接用 `s_t` 表示神经状态向量也可以，但必须在符号表中声明，不能一会儿表示原始历史、一会儿表示编码向量。

### 3.4 候选集合 `C_t`

候选集合是策略网络当前允许进一步比较的物品集合：

```text
C_t = {a_t^1, a_t^2, ..., a_t^K}
```

当前项目中：

```text
HPN 根据 z_t 逐层预测 SID
-> 解码若干 SID path
-> 通过 SID 索引找到候选 item
-> 形成 C_t
```

`C_t` 是物品集合，不是用户反馈集合。

### 3.5 推荐动作 `a_t`

推荐策略网络的动作是：

```text
a_t = 系统最终推荐的一个 item
```

在 HPN 内部，动作生成过程可以表示为 SID 的逐层决策：

```text
a_t = [sid_1, sid_2, ..., sid_L]
```

但最终环境动作仍然落到一个具体推荐物品。

以下变量不是系统动作：

```text
listen
played_ratio
like
dislike
unlike
undislike
```

它们属于用户响应。

### 3.6 用户响应 `y_t`

用户响应是系统推荐物品后观察到的结果。

当前项目适合把它定义为结构化变量：

```text
y_t = (
  listen_t,
  play_t,
  like_t,
  dislike_t,
  unlike_t,
  undislike_t
)
```

其中：

```text
listen_t：是否发生播放
play_t：发生播放后的连续播放完成度
like_t：是否发生 like
dislike_t：是否发生 dislike
unlike_t：是否发生 unlike
undislike_t：是否发生 undislike
```

这些响应不完全互斥。例如：

```text
listen=1
play=0.95
like=1
```

可以同时成立。

### 3.7 即时奖励 `r_t`

即时奖励是把结构化用户响应映射成用于优化的标量：

```text
r_t = R(y_t)
```

当前项目使用最新 `v2 reward`，概念上可写成：

```text
播放贡献
+ like 奖励
- dislike 惩罚
- unlike 惩罚
+ undislike 修正
```

需要区分：

```text
y_t：保留多种反馈含义的结构化响应
r_t：将这些反馈压缩后的一个优化标量
```

奖励不能替代完整响应。两个不同响应可能得到相同奖励，但对下一步偏好建模的含义不同。

###  3.8 下一状态 `s_{t+1}` 与 `z_{t+1}`

用户产生真实响应后，历史更新为：

```text
H_{t+1} = Append(H_t, a_t, y_t, c_t)
```

下一状态表示为：

```text
z_{t+1} = Encoder(H_{t+1})
```

在线系统中，真正进入下一轮推荐的只能是由真实响应更新得到的 `z_{t+1}`。

## 4. Predictor 的正确定位

### 4.1 候选条件预测器

建议把预测器写成：

```text
sigma_t(a) = Predictor(z_t, a)
```

其中 `sigma_t(a)` 不是一个用户动作，也不是一个单独反馈值，而是：

```text
在当前状态 z_t 下推荐候选物品 a 后，可能后果的条件分布描述
```

更完整地可以写为：

```text
sigma_theta(y, z' | z_t, a)
```

表示给定当前状态和候选物品时，用户响应 `y` 与下一状态 `z'` 的联合预测分布。

### 4.2 推荐输出结构

完整设计中，`sigma_t(a)` 应包含：

```text
1. 播放结果分布
2. 显式反馈分布
3. 即时奖励分布或由响应推导的奖励
4. 不同响应分支对应的下一状态
5. 预测不确定性
```

可以表示为：

```text
sigma_t(a) = {
  response_distribution,
  play_distribution,
  reward_distribution,
  branch_next_states,
  uncertainty
}
```

### 4.3 Predictor 不是策略网络

Predictor 回答：

```text
如果推荐 a，用户可能怎样响应，后果可能是什么？
```

策略网络回答：

```text
当前应该推荐哪个 a？
```

Predictor 可以帮助策略比较候选，但不等于策略本身。

### 4.4 Predictor 与用户模拟器的区别

两者都可能学习：

```text
P(y | z_t, a)
```

所以仅从响应预测头看，它们确实有重叠。

区别主要来自使用方式：

```text
候选预测器：
  对当前候选并行预测
  用于当前一步评分
  不把预测反馈永久写入线上历史

用户模拟器：
  从分布中生成一个模拟响应
  将模拟响应写入模拟环境状态
  可以连续滚动很多步生成虚拟轨迹
```

当前项目更接近“候选条件后果预测器 + 一步临时状态价值”，不是完整可持续滚动的用户模拟器。

## 5. 用户响应分布如何定义

### 5.1 五类反馈不是单分类分布

当前五个反馈头应理解为独立边缘概率：

```text
P(listen=1 | z_t, a)
P(like=1 | z_t, a)
P(dislike=1 | z_t, a)
P(unlike=1 | z_t, a)
P(undislike=1 | z_t, a)
```

不能使用一个五分类 softmax，因为 softmax 强制五类概率之和为 1，等价于假设一次只能发生其中一种响应。

### 5.2 独立 sigmoid 仍然只是近似

五个 sigmoid 允许多个反馈同时发生，但通常隐含条件独立近似：

```text
P(y | z,a)
约等于多个边缘概率的乘积
```

现实中响应并不独立：

```text
没有 listen 时，出现高播放完成度不合理
like 和 dislike 同时发生的概率通常很低
like 后可能出现 unlike
dislike 后可能出现 undislike
```

因此完整版本可使用条件分解：

```text
P(y | z,a)
= P(listen | z,a)
× P(play | listen,z,a)
× P(like,dislike,unlike,undislike | listen,play,z,a)
```

第一版使用独立概率可以保持简单和可训练，但论文中应明确这是多标签边缘概率近似，不应直接声称已经准确学习完整联合分布。

### 5.3 播放结果必须是条件分布

播放结果至少包含两层：

```text
是否发生播放
发生播放后的播放完成度
```

合理分解为：

```text
P(listen | z,a)
P(play_ratio | listen=1,z,a)
```

不能直接对所有样本回归一个播放比例，因为没有播放的样本不存在真实播放完成度。

### 5.4 超过 100% 的播放

Yambda 的播放完成度可以超过 100%。因此不能只用严格限制在 `[0,1]` 的单一分布覆盖所有播放行为。

可以拆成：

```text
play_clipped = min(play_ratio, 1)
play_excess = max(play_ratio - 1, 0)
```

再分别预测：

```text
P(play_clipped | listen,z,a)
P(play_excess > 0 | listen,z,a)
P(play_excess | play_excess > 0,listen,z,a)
```

工程初版也可以预测播放区间概率：

```text
0% 到 20%
20% 到 50%
50% 到 80%
80% 到 100%
超过 100%
```

区间分布比单个均值更适合后续响应分支采样。

## 6. 即时奖励分布如何处理

### 6.1 奖励由响应确定时

如果奖励规则完全确定：

```text
r = R(y)
```

那么理论上不必再学习独立奖励分布。可以先采样响应 `y`，再直接计算 `R(y)`。

优点：

```text
响应和奖励严格一致
奖励含义可解释
修改 reward 权重时不必重新定义标签关系
```

### 6.2 为什么仍可能保留奖励头

当前日志聚合、撤销规则和延迟反馈使奖励不一定只由简单响应向量确定，因此可以保留辅助奖励头：

```text
P(r | z,a)
```

或预测：

```text
E[r | z,a]
```

但必须避免两套互相矛盾的奖励：

```text
由响应计算出的 reward
独立 reward head 输出
```

推荐做法是：

```text
主候选价值优先使用响应分支对应的 R(y)
奖励头用于辅助校准或建模未被响应字段解释的残差
```

### 6.3 当前实现

当前代码输出的是一个有界奖励点估计：

```text
predicted_reward ∈ [-2,2]
```

它不是完整奖励分布。

因此当前能计算的是近似期望奖励，不能从奖励头本身采样多个不同奖励场景。

## 7. 响应分支对应的下一状态

### 7.1 为什么不同响应必须对应不同下一状态

同一个候选物品可能产生不同响应：

```text
分支 1：完整播放并 like
分支 2：播放 10% 后离开
分支 3：dislike
```

这些响应对用户后续状态的影响不同，所以应构造：

```text
z_{t+1}^{(1)} = Update(z_t,a,y^{(1)})
z_{t+1}^{(2)} = Update(z_t,a,y^{(2)})
z_{t+1}^{(3)} = Update(z_t,a,y^{(3)})
```

不能只为候选物品 `a` 构造一个与响应无关的固定下一状态。

### 7.2 Update 的含义

理想情况下：

```text
Update(z_t,a,y)
= Encoder(Append(H_t,a,y))
```

但在线候选比较时，对所有候选和所有响应分支重新运行完整历史 Transformer 成本很高。

因此当前工程使用近似更新器：

```text
soft_next_state = SoftStateBuilder(z_t,a,y)
```

它学习接近真实追加历史后由 `StateEncoder` 得到的下一状态表示。

### 7.3 不要先平均响应再做非线性更新

以下两个量通常不相等：

```text
V(Update(z,a,E[y]))

E_y[V(Update(z,a,y))]
```

原因是 `Update` 和 `V` 都是非线性函数。

例如：

```text
50% 概率 like，价值 +2
50% 概率 dislike，价值 -2
```

先把反馈平均成“既不喜欢也不讨厌”的中性向量，再更新状态，可能得到价值 `+0.8`；但真实分支价值期望是：

```text
0.5 × 2 + 0.5 × (-2) = 0
```

所以完整实现应保留多个响应分支，分别更新和估值后再求期望。

### 7.4 当前实现的近似

当前 `SoftStateBuilder` 可以接收预测概率或采样后的反馈向量，但普通在线重排主要使用概率期望形成一个临时软状态。

这比完全不建模下一状态更完整，但仍不等于“所有响应分支分别更新”。

要严格实现本文候选价值公式，在线评分阶段需要对每个候选采样或枚举多个 `y`，分别生成 `z_{t+1}^{(m)}`。

## 8. 候选价值公式

### 8.1 离散响应情形

如果响应集合有限，候选价值定义为：

```text
Q(z_t,a)
= Σ_y P(y | z_t,a)
  × [R(y) + gamma × V(Update(z_t,a,y))]
```

含义是：

```text
对推荐 a 后所有可能用户响应逐一考虑
每个响应分支计算即时奖励和下一状态长期价值
按照该响应发生概率加权求和
```

### 8.2 连续播放情形

播放完成度是连续变量时，严格形式包含积分：

```text
Q(z_t,a)
= E_{y ~ sigma_t(a)}[
     R(y) + gamma × V(Update(z_t,a,y))
   ]
```

这里的期望同时覆盖：

```text
listen 是否发生
连续播放完成度
四类显式反馈组合
其他需要建模的上下文变化
```

### 8.3 多次采样近似

完整枚举所有反馈组合和连续播放值通常不可行，因此使用 `M` 次采样：

```text
y^(m) ~ sigma_t(a)
```

候选价值近似为：

```text
Q_hat(z_t,a)
= 1/M × Σ_{m=1}^M [
    R(y^(m))
    + gamma × V(Update(z_t,a,y^(m)))
  ]
```

这里“多次采样”不是只在训练时使用的优化技巧。它是在无法精确计算响应期望时，对候选价值积分进行数值近似的方法。

训练和在线都可以使用：

```text
训练：构造价值目标和学习分支状态
在线：估计每个候选物品的期望价值
```

在线采样次数通常小于离线训练，以控制延迟。

## 9. 先平均后最大与先最大后平均

### 9.1 两个不同问题

给定候选集合 `C_t` 和响应场景 `sigma`，存在两种不同顺序：

```text
max_a E_y[Q(a,y)]
```

以及：

```text
E_sigma[max_a Q(a,sigma)]
```

二者一般不相等。

### 9.2 先对每个候选求期望，再选候选

```text
a* = argmax_a E_y[Q(a,y)]
```

表示系统在不知道真实响应结果前，选择期望价值最高的一个固定动作。

这最符合普通在线推荐，因为系统推荐前不能知道用户将落在哪个响应分支。

### 9.3 每个场景先选最好动作，再对场景平均

```text
E_sigma[max_a Q(a,sigma)]
```

表示每个预测场景中都允许选不同的最好动作，再对这些最好结果平均。

这个目标更乐观，因为它仿佛允许策略提前知道当前属于哪个场景。

Bellman-Jensen 中的先最大后平均有其特定预测分布和价值定义。迁移到推荐任务时必须说明 `sigma` 表示什么，以及线上是否真的可以在决策前获得区分场景的信息。

### 9.4 当前项目建议

在线候选选择的主公式建议采用：

```text
a_t
= argmax_{a∈C_t}
  E_{y~sigma_t(a)}[
    R(y) + gamma V(Update(z_t,a,y))
  ]
```

Bellman-Jensen 风格的：

```text
E_sigma[max_a(...)]
```

可以作为离线价值目标或对照实验，但不能在没有额外论证时直接替代在线可执行决策公式。

## 10. 最终候选评分

### 10.1 HPN 原始分数

HPN 给出候选生成分数：

```text
base_score(a)
```

它表示当前策略网络对候选物品的偏好或生成可能性。

### 10.2 预测候选价值

Predictor 与 ValueHead 给出：

```text
future_value(a)
= E_y[R(y) + gamma V(Update(z_t,a,y))]
```

### 10.3 合并方式

最终排序可以写为：

```text
final_score(a)
= normalize(base_score(a))
+ alpha × normalize(future_value(a))
- beta × epistemic_uncertainty(a)
```

其中：

```text
alpha：未来候选价值权重
beta：模型认知不确定性惩罚权重
```

归一化用于避免 HPN logit 和价值分数数值范围差异过大。

但归一化只能统一当前候选集合内的相对尺度，不能证明两个模块已经概率校准。

## 11. 预测不确定性

### 11.1 两类不确定性

第一类是结果本身随机：

```text
偶然不确定性
```

例如同一用户在相同状态下对同一首歌有时完整播放、有时提前离开。这种不确定性由响应分布本身表示。

第二类是模型不知道：

```text
认知不确定性
```

例如某个候选物品在训练数据中几乎没被推荐给相似用户，模型输出缺乏数据支持。

### 11.2 响应熵不等于全部不确定性

二值反馈概率接近 0.5 时熵较高，说明预测结果本身分散。

但概率接近 0 或 1 不一定说明模型可靠。模型也可能因为训练数据外推而过度自信。

因此：

```text
响应分布熵：主要反映结果分散程度
模型集成方差：更适合反映认知不确定性
```

### 11.3 可实现方法

认知不确定性可以使用：

```text
多个独立 Predictor 的模型集成
不同随机初始化的头部集成
测试阶段保留 dropout 的多次前向
参数后验近似
```

例如使用 `E` 个模型：

```text
uncertainty(a)
= 模型之间 predicted Q(z_t,a) 的方差
```

### 11.4 当前代码状态

当前代码没有完整实现独立的不确定性估计模块。

以下变量不能直接叫作预测不确定性：

```text
regret_probs
response_probs
candidate value
```

`regret_probs` 表示预测负面后果风险，不等于模型对自身预测是否可靠。

所以当前论文或文档不能声称“已经实现预测不确定性惩罚”，除非后续真正加入模型集成、重复前向方差或其他可靠估计。

## 12. 离线训练数据能监督什么

### 12.1 日志动作的监督

离线日志在状态 `z_t` 下只观察到一个实际物品：

```text
a_logged
```

以及它的真实响应：

```text
y_logged
```

因此 Predictor 的直接监督为：

```text
Predictor(z_t,a_logged) -> y_logged
```

### 12.2 未推荐候选没有反事实标签

对于同一状态下没有真正推荐的候选：

```text
a_not_logged
```

日志中不存在其真实响应。

不能把“用户没有响应”直接标成：

```text
listen=0, like=0, dislike=0, ...
```

因为用户根本没有看到它。

这就是离线推荐中的反事实缺失问题。

### 12.3 候选外推风险

在线重排会对 HPN 的多个候选调用 Predictor，但 Predictor 主要在日志动作上训练。

如果候选远离日志策略的数据支持范围，预测可能不可靠。

可采用：

```text
限制候选来自行为策略支持较高的区域
加入物品和状态相似度约束
使用认知不确定性惩罚
使用保守价值目标
报告候选覆盖与支持度
```

不能只因为 Predictor 能对任意向量前向计算，就认为这些候选的预测都可信。

## 13. Predictor 离线训练目标

### 13.1 多标签反馈损失

五类响应使用二元交叉熵：

```text
L_response
= Σ_j BCE(p_j, y_j)
```

显式反馈稀疏时使用按训练集正例数计算的类别权重。

### 13.2 播放分布损失

完整版本应使用负对数似然：

```text
L_play
= -log P(play_ratio | listen=1,z_t,a)
```

当前实现是播放点估计的平滑回归损失，只在 `listen=1` 时计算。

### 13.3 奖励损失

当前为：

```text
L_reward
= MSE(predicted_reward, reward_v2)
```

如果后续改为奖励分布，应使用相应分布的负对数似然和校准指标。

### 13.4 后悔辅助损失

```text
L_regret
= CrossEntropy(predicted_regret_type, regret_type)
```

### 13.5 分支下一状态损失

对日志中真实发生的响应分支：

```text
L_state
= ||Update(z_t,a_logged,y_logged) - z_{t+1}||^2
```

当前代码已经对真实日志分支提供这一监督。

未发生的响应分支没有真实下一状态，不能直接使用监督损失，只能通过共享结构、价值目标或模型假设进行泛化。

### 13.6 总 Predictor 损失

当前可以写成：

```text
L_predictor
= lambda_response × L_response
+ lambda_play × L_play
+ lambda_reward × L_reward
+ lambda_regret × L_regret
```

默认：

```text
lambda_response = 1.0
lambda_play = 0.1
lambda_reward = 0.1
lambda_regret = 0.1
```

状态更新器和 ValueHead 在后续阶段训练。

## 14. ValueHead 的离线训练

### 14.1 一步时序目标

```text
target_td
= r_t + gamma × bootstrap_mask × V_target(z_{t+1})
```

### 14.2 多步日志回报

```text
future_return_t
= r_t + gamma r_{t+1} + ... + gamma^(k-1) r_{t+k-1}
```

当前实现只在相同数据切分内部累计，不能跨入验证或测试数据。

### 14.3 候选预测目标

对 HPN 候选集合，用 Predictor 构造预测响应和临时下一状态，再形成候选最大化目标。

当前这部分是受 Bellman-Jensen 启发的近似，不等于完整恢复真实环境转移概率。

### 14.4 目标价值网络

使用缓慢更新的目标网络：

```text
V_target <- tau × V + (1-tau) × V_target
```

目的是减少价值目标和当前价值网络同时快速变化导致的不稳定。

## 15. 在线推荐完整流程

### 15.1 第一步：构造当前真实状态

读取用户截至当前已经发生的真实历史：

```text
H_t
```

编码得到：

```text
z_t = StateEncoder(H_t)
```

禁止读取该时间步之后的真实反馈。

### 15.2 第二步：HPN 生成候选

```text
C_t = HPN(z_t)
```

并保留每个候选的基础分数：

```text
base_score(a)
```

### 15.3 第三步：逐候选预测响应分布

对每个：

```text
a ∈ C_t
```

计算：

```text
sigma_t(a) = Predictor(z_t,a)
```

### 15.4 第四步：生成响应分支

完整实现可以对每个候选采样：

```text
y_a^(1), y_a^(2), ..., y_a^(M)
```

每个响应样本必须满足基本结构约束，例如未播放时不能生成正的播放完成度。

### 15.5 第五步：构造分支下一状态

```text
z_{t+1,a}^{(m)}
= Update(z_t,a,y_a^(m))
```

### 15.6 第六步：计算候选期望价值

```text
Q_hat(z_t,a)
= 1/M × Σ_m [
    R(y_a^(m))
    + gamma V(z_{t+1,a}^{(m)})
  ]
```

### 15.7 第七步：候选重排

```text
final_score(a)
= normalize(base_score(a))
+ alpha normalize(Q_hat(z_t,a))
- beta uncertainty(a)
```

选择：

```text
a_t = argmax_{a∈C_t} final_score(a)
```

### 15.8 第八步：等待真实反馈

系统推荐 `a_t` 后，等待用户真实响应：

```text
y_t_real
```

下一轮状态必须使用：

```text
H_{t+1} = Append(H_t,a_t,y_t_real)
```

不能使用某个采样响应 `y_a^(m)` 或软平均响应替代真实反馈。

### 16.1 已实现

```text

Q_current(z,a)
```

```text
E_y[R(y) + gamma V(Update(z,a,y))]
```

## 17. 建议的下一阶段工程结构

### 17.1 响应分布对象

建议 Predictor 不只返回散乱张量，而是统一返回：

```text
ResponseDistributionOutput
```

至少包含：

```text
listen_prob
explicit_feedback_probs
play_distribution_params
reward_distribution_params
```

并提供统一方法：

```text
sample(M)
expected_response()
log_prob(observed_response)
entropy()
```

### 17.2 分支更新对象

建议新增清晰接口：

```text
BranchStateUpdater(z_t, candidate_features, sampled_response)
-> branch_next_state
```

输入输出都应保留：

```text
[batch, candidate_k, sample_m, dimension]
```

避免在不同函数里反复展平和恢复维度导致候选与采样位置错位。

### 17.3 候选价值计算器

建议单独实现：

```text
CandidateValueEstimator
```

职责仅包括：

```text
从 Predictor 分布采样响应
计算每个响应的 reward
构造分支下一状态
调用 ValueHead
对响应分支求期望
返回候选价值和诊断信息
```

不负责 HPN 候选生成，也不负责永久更新用户历史。

### 17.4 不确定性估计器

建议认知不确定性作为独立模块：

```text
UncertaintyEstimator
```

不要把 `regret_probs` 改名成不确定性。

## 19. 具体示例

### 19.1 当前状态

假设用户最近历史为：

```text
歌曲 甲：播放 95%，like
歌曲 乙：播放 15%
歌曲 丙：播放 110%，like
```

状态编码器得到：

```text
z_t
```

HPN 给出两个候选：

```text
a_1 = 歌曲 丁
a_2 = 歌曲 戊
```

### 19.2 Predictor 输出

对歌曲丁：

```text
listen 概率：0.90
高完成度概率：0.75
like 概率：0.55
dislike 概率：0.05
unlike 概率：0.03
```

对歌曲戊：

```text
listen 概率：0.70
高完成度概率：0.40
like 概率：0.20
dislike 概率：0.10
unlike 概率：0.08
```

### 19.3 响应分支

歌曲丁可能采样出：

```text
分支 1：完整播放 + like
分支 2：播放 70%，无显式反馈
分支 3：播放 10% 后离开
```

对应：

```text
Q_1 = 1.6 + gamma × 0.9
Q_2 = 0.4 + gamma × 0.5
Q_3 = -0.8 + gamma × (-0.2)
```

若概率分别为：

```text
0.5、0.3、0.2
```

则歌曲丁候选价值为：

```text
Q(丁)
= 0.5 × Q_1
+ 0.3 × Q_2
+ 0.2 × Q_3
```

这不是掩码操作。Predictor 改变的是候选物品在不同可能用户响应下的预期长期后果，再由该后果参与最终排序。

### 19.4 为什么不能直接选择 like 概率最大的物品

某物品可能：

```text
like 概率很高
但 unlike 概率也高
播放完成度低
预测下一状态价值差
```

另一个物品可能：

```text
like 概率中等
完整播放概率高
负反馈风险低
长期状态价值高
```

候选价值公式会综合这些分支，而不是只看一个反馈概率。

## 20. 常见错误

### 20.1 把用户响应叫作动作

错误：

```text
动作有 listen、like、dislike、unlike、undislike 五种
```

正确：

```text
系统动作是推荐 item
五类事件是用户响应
```

### 20.2 把五个概率做平均

错误：

```text
把 listen、like、dislike、unlike、undislike 概率直接平均成一个反馈值
```

原因：正负反馈含义相反，播放与显式反馈量纲不同。

正确做法是保留结构化响应，通过明确奖励函数和分支价值整合。

### 20.3 把概率最大的反馈当作唯一反馈

错误：

```text
只取五个概率中最大的类型
```

原因：多种响应可以共同发生。

### 20.4 把 soft next state 保存为真实历史

错误：

```text
把候选预测出来的下一状态写入下一轮用户历史
```

正确：

```text
soft next state 仅用于当前候选评分
下一轮使用真实响应更新状态
```

### 20.5 把后悔风险叫作不确定性

错误：

```text
unlike 概率高，所以模型不确定性高
```

正确：

```text
unlike 概率高表示预测负面结果风险高
模型间预测差异大才更接近认知不确定性高
```

### 20.6 对未曝光候选伪造负标签

错误：

```text
某候选没有出现在日志中，所以标记为所有反馈都为 0
```

正确：

```text
没有曝光就没有反事实响应标签
```

### 20.7 训练时使用完整用户池化

错误：

```text
先用用户全部会话计算一个用户向量，再拿它构造早期训练状态
```

这会把未来验证和测试行为泄漏到训练状态。

正确做法是按时间前缀递增更新用户记忆。

## 21. 术语对照表

```text
H_t：决策前可观察用户历史
s_t：强化学习状态
z_t：状态编码向量
C_t：HPN 产生的候选物品集合
a_t：系统最终推荐的物品
y_t：用户对推荐物品的结构化响应
r_t：由响应映射得到的即时奖励
sigma_t(a)：候选物品条件下的预测后果分布
Update：根据候选和响应构造下一状态的更新函数
z_{t+1}：下一状态编码
V(z)：从状态出发的长期价值
Q(z,a)：在状态 z 下选择候选 a 的价值
gamma：未来价值折扣系数
M：每个候选的响应采样次数
K：候选物品数量
```

## 22. 当前推荐的论文方法定义

可以将方法定义为：

```text
给定由真实历史编码得到的当前状态 z_t，HPN 生成候选物品集合 C_t。
候选条件 Predictor 对每个 a∈C_t 估计结构化用户响应分布
sigma_theta(y|z_t,a)。对预测响应分支分别计算即时奖励，并通过可学习状态
更新器得到临时下一状态。候选价值由响应概率加权的即时奖励与下一状态价值
之和给出。最终策略结合 HPN 基础分数和预测候选价值选择推荐物品。
在线下一状态始终由真实用户反馈更新，预测分支不会写入真实交互历史。
```

数学形式：

```text
z_t = Encoder(H_t)

C_t = HPN(z_t)

sigma_t(a) = Predictor(z_t,a)

Q_hat(z_t,a)
= E_{y~sigma_t(a)}[
    R(y) + gamma V(Update(z_t,a,y))
  ]

a_t
= argmax_{a∈C_t}
  [normalize(base_score(a))
   + alpha normalize(Q_hat(z_t,a))
   - beta uncertainty(a)]

H_{t+1}
= Append(H_t,a_t,y_t_real)
```

## 23. 实施顺序建议

要从当前近似升级到完整响应分支价值，建议按以下顺序：

1. 先把播放点回归改为条件播放分布，并验证概率校准。
2. 实现统一的响应分布采样接口，保证采样结果满足结构约束。
3. 将 `SoftStateBuilder` 扩展为显式接收 `[候选, 采样分支]` 张量。
4. 实现 `CandidateValueEstimator`，逐分支调用 ValueHead 后求期望。
5. 在线重排改用逐响应分支期望价值，而不是单个平均 soft state。
6. 增加 Predictor 集成，得到认知不确定性。
7. 加入候选数据支持度诊断和保守惩罚。
8. 完成 HPN、一步预测价值、多分支预测价值三组消融。
9. 最后再讨论 Bellman-Jensen 的先最大后平均目标是否适合作为主公式。

## 24. 最终边界

本项目中必须始终保持：

```text
推荐动作 = 系统推荐的 item
用户响应 = 播放和显式反馈
预测分布 = 当前状态与候选 item 条件下的可能后果
预测下一状态 = 只用于当前候选估值的临时分支
真实下一状态 = 由线上真实反馈更新得到
```

候选价值的核心不是对预测结果做简单掩码，而是对候选物品可能造成的多种响应后果进行概率加权的长期价值比较。
