# 6.26 Future-Aware Predictor 方法设计大纲

本文档是 `0626 Predictor` 工作区的方法设计与工程记录。主体代码位于本目录；为统一推荐时间步口径，只对共享的 `Regret/scripts/02_split_transitions.py` 做了必要扩展，未另造一套原始事件切分逻辑。

## 0. 当前共识

### 0.1 目标

在现有 Yambda / HSRL / Regret 框架中，引入一个新的 future-aware predictor，用于在最终推荐动作确定之前，对 HPN 产生的候选物品进行未来后果预测，并用预测结果修正候选排序。

当前最合理的定位是：

```text
HPN 负责生成候选集
future predictor 负责预测候选物品的未来后果
soft state update 负责构造临时预测下一状态
value head 负责把预测下一状态转成长远价值
final scorer 负责合并 HPN 分数和未来价值，决定最终推荐
```

简写：

```text
HPN candidate generation
-> action-conditioned future consequence prediction
-> soft predicted next state
-> Bellman-style value scoring
-> future-aware scoring
-> candidate reranking
```

### 0.2 不能违反的边界

1. 在线推荐时不能使用真实未来反馈。
2. 真实未来行为只能在离线训练中作为监督标签。
3. predictor 的预测结果不能永久写入用户真实历史。
4. 每个在线时间步都要基于当前真实历史重新生成预测信息 `sigma_t`。
5. 如果需要临时构造预测下一状态，只能用于当前候选物品打分，不能当作线上真实状态保存。
6. `listen / like / dislike / unlike / undislike` 是用户响应事件，不是系统动作。
7. 系统动作是推荐哪个 item 或哪个 SID path。
8. 如果不区分 predictor 与 simulator，模块会退化成另一个用户响应模型，论文贡献会变弱。

### 0.5 2026-07-17 实现口径修订

本节是当前代码的权威口径；与后文早期设想冲突时，以本节为准。

#### 0.5.1 推荐时间步

不再把每条原始事件当成一个推荐时间步。预处理直接复用
`Regret/scripts/02_split_transitions.py` 的 `session_run`：先按时间间隔切分会话，再把同一会话内连续出现的同一物品及其响应聚合成一个时间步。

例如连续记录为：

```text
歌曲 A：listen 80%
歌曲 A：like
歌曲 B：listen 20%
```

会构成两个时间步。歌曲 A 的目标可以同时为 `listen=1, like=1`，而不是把播放和点赞拆成两个系统动作。聚合窗口内的响应只作为当前候选物品的离线监督标签，不会进入该时间步的状态；到下一个时间步时，它才成为已观察历史，因此不构成未来状态泄漏。

#### 0.5.2 状态定义

状态由决策时已经发生的用户历史动态编码，不是一个预先保存的单独向量。当前共享状态编码器输入：

```text
历史物品 embedding
五维历史响应向量
播放完成度与超过 100% 的部分
是否自然产生的交互
相邻时间步间隔
是否属于当前会话
序列位置与有效位置掩码
```

编码器产生三部分：

```text
完整有序历史的最后状态
当前会话内的短期偏好池化
历史窗口中先前会话的长期偏好池化
```

三者融合为 `state_emb`，供 HPN 与 predictor 使用。会话切分没有丢失：样本保留 `user_id`、`session_id`、`session_step_idx`、`user_step_idx` 和逐位置 `same_session` 标志。

当前“长期”仍受 `history_len=50` 限制，不等于用户终身历史。如果当前会话本身超过 50 个时间步，窗口内可能没有先前会话，长期池化会退化为零向量。这是已知限制；后续可以增加只从训练前缀更新的用户级记忆，但不能先对完整用户历史池化后再切训练、验证和测试，否则会把未来行为带入状态。

#### 0.5.3 预测目标优先级

主要目标是候选条件下的五维非互斥反馈概率：

```text
P(listen | s_t, a)
P(like | s_t, a)
P(dislike | s_t, a)
P(unlike | s_t, a)
P(undislike | s_t, a)
```

这里使用五个独立概率，不使用总和必须为 1 的单分类分布，因为播放和点赞可以同时发生。四类显式反馈标签表示聚合窗口内该原始事件是否实际发生，不使用奖励函数消解撤销关系后的 `effective_*` 字段。连续播放完成度只在 `listen=1` 的样本上计算辅助损失；即时奖励仍按 `v2` 的有效反馈规则生成，由独立的有界奖励头学习，后悔类型也是辅助约束。默认损失权重为：

```text
反馈分布 1.0
播放完成度 0.1
即时奖励 0.1
后悔类型 0.1
```

稀疏显式反馈使用按训练集正例数计算的类别权重，并设置上限，防止极少正例造成梯度爆炸。正式评估必须分别报告五类响应的精确率、召回率和 F1，不能用播放事件占多数的总体准确率代替。

#### 0.5.4 下一状态与切分边界

`next_history` 只由当前真实时间步追加到历史得到，作为离线的下一状态监督。`soft_next_state` 由 predictor 的概率输出临时构造，仅用于候选价值估计；在线不会写回真实用户历史。

多步 `future_return` 只在同一数据切分内部计算。训练集最后一个时间步不会跨界读取验证或测试反馈，并通过 `bootstrap_mask=0` 停止价值自举。这一规则同时避免未来信息泄漏和训练、评估边界混淆。

## 1. 先定义问题对象

### 1.1 状态 `s_t`

当前项目中状态不是一个单独提前保存的向量，而是一组历史特征。

现有 Regret 数据管线中，状态主要包括：

```text
history_ids
history_features
history_feedbacks
history_event_type_ids
history_mask
```

含义：

```text
history_ids:
  历史物品编号

history_features:
  历史物品 embedding，通常是 [H, item_dim]

history_feedbacks:
  历史反馈数值，例如播放比例、正反馈、负反馈、模拟 reward

history_event_type_ids:
  历史事件类型，例如 listen、like、dislike、unlike、undislike

  注意：当前代码里的 recommend 是模拟器内部占位，不是 Yambda 原始事件。

history_mask:
  哪些位置是真实历史，哪些是 padding
```

future predictor 和 HPN 都应该从这个状态定义出发，不能额外偷看未来字段。

### 1.2 系统动作 `a_t`

在当前单物品推荐设定下：

```text
a_t = 推荐一个 item
```

在 HSRL / HPN 中，item 通过 SID path 表示：

```text
a_t = [sid_1, sid_2, ..., sid_L]
```

注意：

```text
like / dislike / unlike 不是动作
```

它们是用户看到推荐之后产生的响应事件。

### 1.3 用户响应 `o_t`

Yambda 原始序列数据中的反馈事件只有五类：

```text
listen
like
dislike
unlike
undislike
```

其中 `listen` 不是 0/1 变量。它对应一次收听事件，并带有 `played_ratio_pct`。代码中会转成：

```text
played_ratio_norm = played_ratio_pct / 100
```

因此：

```text
played_ratio_pct = 80:
  收听了约 80%

played_ratio_pct = 100:
  基本完整收听

played_ratio_pct > 100:
  用户可能回拉进度条、重复收听片段，不能简单截断成 1
```

当前数据字段依据：

```text
multi_event.parquet:
  uid
  timestamp
  item_id
  is_organic
  played_ratio_pct
  track_length_seconds
  event_type
```

`recommend` 不是 Yambda 原始事件字段。它只出现在当前 `RegretUserResponseEnv` 的模拟器内部，用来给“模拟出来没有 listen 或显式反馈”的情况放一个占位事件。新 predictor 的默认原始事件空间不应包含 `recommend`，除非后续明确建模“曝光但无可见反馈”，并能在数据中找到对应监督信号。

Like to Unlike 草稿中的 regret 逻辑应继续保留：

```text
low_play:
  隐式后悔或低参与度

dislike:
  显式负反馈

unlike:
  对曾经喜欢的修正，属于重要的后悔信号

undislike:
  对曾经点踩的修正，可能是偏好恢复信号
```

当前实现中的 reward 统一使用最新主线 `v2`，不使用旧的 `v1`。

`v2` 的核心口径：

```text
play = clip(max_play_ratio, 0, 1)
play_reward = 2 * play - 1      如果存在 listen
play_reward = 0                 如果不存在 listen

reward_raw =
  play_reward
  + 0.8 * effective_like
  - 1.2 * effective_dislike
  - 0.6 * effective_unlike
  + 0.2 * effective_undislike

reward_scaled = clip(reward_raw, -2, 2)
```

注意：

```text
played_ratio_pct > 100 仍然保留给 predictor 学习播放比例。
但计算 v2 reward 时，play 会裁剪到 1。
```

### 1.4 预测信息 `sigma_t`

在本模块中，`sigma_t` 不应该定义成“用户会选择哪个候选 item 的概率”。

更合理的定义是：

```text
sigma_t = 当前状态 s_t 下，对候选动作集合 C_t 的预测后果表
```

候选集合：

```text
C_t = {a_1, a_2, ..., a_K}
```

每个候选动作都有自己的预测信息：

```text
sigma_t(a_i) = {
  response_probs,
  predicted_play_ratio,
  predicted_reward,
  regret_probs,
  soft_next_token,       可选
  next_state_emb,        可选
  lookahead_value,       可选
  uncertainty            可选
}
```

这里的 `response_probs` 指五类原始反馈事件的概率：

```text
listen / like / dislike / unlike / undislike
```

其中 `listen` 还必须配套预测 `played_ratio` 或播放比例桶，不能只当作一个二值点击。

所以 `sigma_t` 的工程形态更像一张候选表：

```text
[B, K, fields]
```

而不是单个向量。

## 2. 新模块定位

### 2.1 不建议定位成纯辅助预测模块

如果只做：

```text
s_t -> future_emb
```

然后把 `future_emb` 拼到 HPN 输入，这更像表征增强。它可以工作，但很难说明“预测信息参与了具体动作决策”。

问题：

```text
它没有回答：如果推荐 A 会怎样，如果推荐 B 会怎样？
```

### 2.2 不建议直接定位成完整 world model

如果做：

```text
s_t, a_t -> sampled response, next_state
```

并在环境中反复 rollout，它就非常接近现有 simulator。

当前项目已有：

```text
RegretUserResponse
RegretUserResponseEnv
```

这部分已经承担了用户响应模拟器角色。新的 future predictor 如果完全重复这条路，贡献会不清楚。

### 2.3 建议定位

建议定位为：

```text
候选动作条件下的未来后果预测器
```

英文可写作：

```text
Action-conditioned Future Consequence Predictor
```

它的职责：

```text
给定当前状态 s_t 和候选动作 a，
预测推荐 a 可能造成的即时反馈、后悔风险、软下一状态和长期价值。
```

它不是替代 HPN，而是在 HPN 给出候选之后参与最终决策。

## 3. 与现有框架的关系

### 3.1 HPN 的角色

HSRL 中 HPN 的核心任务是：

```text
history -> state_emb -> SID token logits -> candidate SID paths
```

当前代码中，基础 HPN / SID policy 的行为是：

```text
history_features -> Transformer -> state_emb -> sid_logits
```

Regret 版本进一步加入：

```text
history_feedbacks
history_event_type_ids
```

所以本模块不应该一开始就改 HPN 主干。优先保持：

```text
HPN = candidate generator
```

### 3.2 future predictor 的角色

future predictor 接收：

```text
s_t
a_i
```

输出：

```text
sigma_t(a_i)
```

它只对 HPN 已经召回的候选动作工作，避免全库预测导致推理成本爆炸。

### 3.3 value head 的角色

value head 是完整实现的一部分，但训练和评估时可以用参数关闭。

原因：

```text
完整方法需要 predicted_reward + gamma * V(soft_next_state)。
本机 smoke 训练可以先只验证 predictor，再打开 value head。
代码层面不拆成两个项目。
```

value head 接收：

```text
soft next state 或 next_state_emb
```

输出：

```text
V(soft_next_state)
```

用于形成候选级前瞻分数：

```text
future_score(a)
= predicted_reward(a)
+ gamma * V(soft_next_state(a))
- regret penalty
```

如果某次本机 smoke 实验临时关闭 value head，则退化为：

```text
future_score(a)
= predicted_reward(a)
```

注意：

```text
value head 不天然等于贝叶斯价值函数。
```

它只是一个价值估计头。只有当它的训练目标采用 Bellman-Jensen 式的：

```text
E_sigma max_a [...]
```

并且 `sigma` 来自预测分布时，才可以称为近似贝叶斯价值函数。否则它只是普通终端价值估计器。

### 3.4 final scorer 的角色

final scorer 合并：

```text
HPN 原始候选分数
future_score
regret risk     可选
uncertainty     可选
```

各项来源：

```text
hpn_logit:
  来自 HPN 对候选 SID path 的逐层 log probability。

future_score:
  完整版本来自 predictor 的 predicted_reward 和 value head 的 gamma * V(soft_next_state)。
  smoke 模式可以临时只用 predicted_reward 检查 predictor 是否可学。

regret risk:
  来自 predictor 输出的 regret_probs，例如低播放比例、dislike、unlike 风险。
  如果初版不单独输出 regret_probs，可以先不单独使用这一项。

uncertainty:
  只能来自多模型集成、dropout 多次前向、校准残差或置信度估计。
  如果没有这些机制，初版不应凭空加入 uncertainty。
```

量纲处理原则：

```text
不能直接把 log probability、reward、value、risk 生硬相加。
```

初版建议只使用：

```text
final_logit(a)
= normalize(hpn_logit(a))
+ alpha * normalize(future_score(a))
```

其中 `normalize` 在验证集上统计均值和标准差，或用温度/线性校准层学习尺度。等 regret risk 和 uncertainty 的来源可靠后，再加入：

```text
- eta * normalize(regret_risk(a))
- beta * normalize(uncertainty(a))
```

得到：

```text
final_logit(a)
```

最终推荐：

```text
argmax_a final_logit(a)
```

## 4. 为什么接法 C 是决策前引入未来预测

接法 C：

```text
HPN 先生成候选
future predictor 再预测候选未来后果
final scorer 最后确定推荐
```

这仍然是决策前引入未来信息，因为 HPN 候选不是最终动作。

区别：

```text
HPN top-k:
  只是候选池

future-aware reranking:
  决定最终推荐哪个 item
```

它不是普通掩码。

普通掩码：

```text
item A 可推荐
item B 不可推荐
```

future-aware reranking：

```text
item A 当前吸引力高，但未来 dislike 风险大
item B 当前吸引力中等，但未来状态价值高
item C 当前和未来都弱
```

形式可能都是：

```text
logit += adjustment
```

但语义不同：

```text
掩码是约束可行性
future score 是预测后果后修正偏好
```

## 5. 离线训练信息边界

### 5.1 离线训练可以用的信息

可用作输入：

```text
当前历史 s_t
当前日志动作 a_t
当前 item feature
当前 SID path
```

可用作监督标签：

```text
当前响应 o_t
当前 reward r_t
下一状态 s_{t+1}
未来 k 步 reward
未来 k 步 regret signal
未来 k 步事件统计
```

### 5.2 离线训练不能做的事

不能把下面这些作为 actor 或 predictor 的输入：

```text
真实 future item 序列
真实 future reward
真实 future regret
真实 next item
真实 next_state 中发生在 a_t 之后的事件
```

它们只能作为标签。

### 5.3 数据集是否要和 simulator 区分

原始 transition 数据可以共用，但建议构造两个不同的数据视图：

```text
response dataset:
  训练 simulator / user response model
  重点是一步响应拟合

future dataset:
  训练 future predictor / value head
  重点是未来后果、soft next state、lookahead value
```

原因：

```text
如果不区分，future predictor 很容易变成另一个 simulator。
```

## 6. future predictor 的输入输出设计

### 6.1 输入

建议输入：

```text
history_features: [B, H, item_dim]
history_feedbacks: [B, H]
history_event_type_ids: [B, H]
history_mask: [B, H]
action_features: [B, item_dim]
action_sid: [B, L] 可选
prior_stats: [B, d_prior] 可选
```

其中：

```text
item_dim:
  当前通常是 128

d_model:
  predictor 内部维度，建议先和 HPN 的 sasrec_d_model 对齐
```

### 6.2 Transformer 是否合理

使用 Transformer 合理，但必须是 action-conditioned。

合理形式：

```text
Transformer 编码历史
候选 action 作为 query 或额外 token
输出该 action 的未来后果
```

不建议的形式：

```text
只输入历史，预测未来真实 item 序列
```

原因：

```text
那只是预测日志策略下接下来会发生什么，
不能回答“如果现在推荐另一个 item 会怎样”。
```

### 6.3 输出

完整实现输出：

```text
response_probs: [B, 5]
predicted_play_ratio: [B]
play_bucket_probs: [B, P] 可选
predicted_reward: [B]
regret_probs: [B, R]
soft_next_token: [B, d_model]
next_state_emb: [B, d_model]
lookahead_value: [B]
uncertainty: [B] 可选
```

其中：

```text
response_probs:
  listen / like / dislike / unlike / undislike

P:
  播放比例桶，例如低、中、高、超过 100%
  注意这只是对 played_ratio_pct 的离散化，不等于 listen 是 0/1

R:
  none / low_play / dislike / unlike
```

初版必须优先把 `predicted_play_ratio` 定义清楚。因为 Yambda 的 `listen` 带连续播放比例，若只预测 `listen_prob`，会丢失“听了多少”和“是否回拉进度条”的信息。

`regret_probs` 不是 Yambda 原始字段，而是从响应和播放比例派生出来的风险标签。

可行定义示例：

```text
dislike 风险:
  当前或未来短窗口出现 dislike

unlike 风险:
  对过去 like 过的 item 后续出现 unlike

low_play 风险:
  listen 事件存在，但 played_ratio_pct 很低
  阈值需要数据审计后确定，例如 20% 或 30%，不能先拍死

rewind / replay:
  played_ratio_pct > 100 不应直接当后悔。
  它更可能表示回拉进度条或重复听，具体含义要结合业务解释。
```

`uncertainty` 也不是原始标签。

严格来源只能是：

```text
多模型集成的预测方差
dropout 多次前向的预测方差
校准模型给出的置信度残差
response_probs 的熵
```

其中 `response_probs` 的熵只能说明“预测分布分散”，不等于模型一定错。初版如果没有做校准或多次预测，不应把 `uncertainty` 放进 scorer。

### 6.4 `sigma_t(a)` 的工程对象

对一个候选动作 `a`：

```text
sigma_t(a) = {
  response_probs,
  predicted_play_ratio,
  play_bucket_probs,
  predicted_reward,
  regret_probs,
  soft_next_token,
  next_state_emb,
  lookahead_value,
  uncertainty
}
```

对候选集：

```text
sigma_t(C_t) = stack([sigma_t(a_1), ..., sigma_t(a_K)])
```

维度：

```text
response_probs: [B, K, 5]
predicted_play_ratio: [B, K]
predicted_reward: [B, K]
lookahead_value: [B, K]
final_logit: [B, K]
```

## 7. soft state update 设计

soft state update 是完整实现的一部分。它的作用是：在需要 `V(soft_next_state)` 或显式 `k >= 2` 前瞻时，构造一个临时的、由预测分布诱导的下一状态表示。

对应 Bellman-Jensen 原文中的抽象对象：

```text
P(s' | s, a, sigma)
```

论文在有限状态空间中可以直接使用预测转移概率。推荐系统的状态是长历史序列和连续 embedding，无法枚举所有 `s'`，因此 `soft_next_state` 是对“预测下一状态期望表示”的工程近似。

它符合原文“用预测转移辅助决策”的抽象设定，但不是原文矩阵形式的精确实现。

### 7.1 为什么不用采样更新

采样更新：

```text
从 response_probs 里采样一个事件
把采样事件写进历史
```

这更像 simulator rollout。

本模块更适合：

```text
期望式 soft update
```

原因：

1. 推理更稳定。
2. 不需要多次随机采样。
3. 更适合候选重排。
4. 不把预测结果伪装成真实历史。

### 7.2 soft future token

对候选 `a`：

```text
soft_event_emb(a)
= sum_e p(e | s_t, a) * event_emb(e)
```

再组合：

```text
soft_future_token(a)
= W_item item_emb(a)
+ soft_event_emb(a)
+ W_reward predicted_reward(a)
+ W_regret regret_probs(a)
+ W_source predicted_source_emb
```

如果使用播放比例，应额外加入：

```text
+ W_play predicted_play_ratio(a)
```

其中 `predicted_source_emb` 必须存在，用来标明：

```text
这个 token 是预测出来的，不是真实历史。
```

### 7.3 临时下一状态

```text
soft_next_state(a)
= Encode([真实历史 tokens, soft_future_token(a)])
```

用途：

```text
1. 给 value head 估计 V(soft_next_state(a))
2. 给显式 k>=2 前瞻提供第二步预测的临时输入
```

注意：

```text
soft_next_state(a) 只用于 score(a)
不写入线上用户真实历史
```

在线下一步仍然使用真实反馈更新后的真实状态。

如果某次本机 smoke 实验只做：

```text
final_logit = normalize(hpn_logit) + alpha * normalize(predicted_reward)
```

则可以通过参数暂时不构造 `soft_next_state`，但代码仍保留完整实现。

## 8. 离线训练阶段设计

### 8.1 阶段 A：预训练 future predictor

输入：

```text
s_t, a_t
```

其中 `a_t` 来自日志中实际曝光或实际交互的 target item。

标签：

```text
当前事件类型
当前播放比例 played_ratio_pct 或播放桶
当前 reward
当前 regret type
下一状态 embedding
未来 k 步累计 reward
```

基础损失：

```text
L_event:
  五类事件类型交叉熵或多标签损失

L_play:
  连续播放比例回归损失，或播放桶交叉熵

L_reward:
  reward 均方误差或平滑绝对误差

L_regret:
  regret type 分类损失

L_next:
  next_state_emb 对齐损失
```

总损失：

```text
L_pred
= lambda_event * L_event
+ lambda_play * L_play
+ lambda_reward * L_reward
+ lambda_regret * L_regret
+ lambda_next * L_next
```

### 8.2 阶段 B：训练 value head

value head 是完整实现的一部分。它用于：

```text
predicted_reward(a)
+ gamma * V(soft_next_state(a))
```

本机 smoke 模式可以先关闭它验证 predictor，但正式方法保留它。

#### 8.2.1 不把日志回报监督作为主路线

日志回报监督指：

```text
G_t^k = r_t + gamma r_{t+1} + ... + gamma^{k-1} r_{t+k-1}
```

训练：

```text
V(s_t) -> G_t^k
```

这个目标只能作为诊断基线，不能作为本文方法的主要贡献。

原因：

```text
G_t^k 来自日志策略已经发生的未来。
它回答的是“历史系统当时那样推荐后，后来获得多少回报”。
它没有回答“如果当前从候选集中重新选择另一个 item，会得到多少回报”。
```

所以它的问题是：

```text
学到的是日志策略下的未来价值，不是候选决策下的最优预测价值。
```

如果只用这个路线，future-aware module 很容易退化成：

```text
用未来标签训练一个状态打分器
```

这和 Bellman-Jensen 的“预测分布下先选最优动作”不一致。

#### 8.2.2 主路线：Bellman-style target

更合理的 value head 目标是：

对状态 `s_t`，先取 HPN 候选集 `C_t`，再对候选预测：

```text
target_V(s_t)
= average_m [
    max_{a in C_t}
    predicted_reward_m(s_t, a)
    + gamma * V(soft_next_state_m(s_t, a))
  ]
```

其中：

```text
m:
  第 m 个预测场景，可以来自 response_probs / played_ratio / reward 的采样，
  也可以先用确定性的期望预测，即 M = 1。

soft_next_state_m(s_t, a):
  只是在训练 target 中临时构造的预测下一状态表示。

max_{a in C_t}:
  表示在同一个预测场景下，系统会选择预测价值最高的候选动作。

average_m:
  表示对不同预测场景的不确定性取平均。
```

这对应“先 max 后 average”的含义：

```text
每个可能世界里先选最优动作，
再把不同可能世界下的最优价值平均。
```

如果本机 smoke 模式不做多次采样，可以先退化成：

```text
target_V(s_t)
= max_{a in C_t}
    predicted_reward(s_t, a)
    + gamma * V_target(soft_next_state(s_t, a))
```

这里的 `V_target` 应该是延迟更新或冻结拷贝，避免训练时目标剧烈震荡。

优点：

```text
更接近 Bellman-Jensen 的先 max 后 average
```

缺点：

```text
工程复杂，依赖预测器质量，容易放大预测误差
```

因此工程顺序应是：

```text
先训练 predictor
再冻结 predictor 做 rerank
再训练 value head
最后做 predictor + value + scorer 的完整评估
```

### 8.3 预训练 predictor 是否等于离线贝叶斯价值函数训练

不等于。

区别：

```text
future predictor:
  学“如果当前候选动作是 a，用户可能产生什么响应，后果价值如何”

Bayesian value function:
  学“在状态 s 下，利用预测分布做决策后，最多能获得多少长期价值”
```

所以：

```text
单独训练 predictor
不是贝叶斯价值函数训练
```

只有当我们额外训练：

```text
V_Bayes(s)
```

并且它的 target 使用：

```text
E_sigma max_a [...]
```

才更接近 Bellman-Jensen 的离线贝叶斯价值函数训练。

### 8.4 是否冻结

建议顺序：

1. 先独立训练 future predictor。
2. 冻结 predictor，接入 HPN top-k reranker，验证离线排序指标。
3. 再考虑训练 value head。
4. 最后才考虑 predictor 与 scorer 联合训练。

理由：

```text
如果一开始联合训练，actor 可能会利用 predictor 的漏洞，
导致 predictor 不再表示真实未来后果。
```

## 9. 在线推荐阶段设计

### 9.1 在线信息

在线可用：

```text
当前真实历史 s_t
HPN 当前候选集 C_t
候选 item feature
候选 SID path
future predictor 输出的 sigma_t(C_t)
```

在线不可用：

```text
真实未来反馈
真实下一状态
真实未来 k 步 reward
```

### 9.2 在线流程

```text
1. 编码当前真实历史 s_t
2. HPN 生成 top-k 候选 C_t
3. 对每个候选 a_i 调用 future predictor
4. 得到 sigma_t(a_i)
5. 如果启用 value head 或 k>=2，临时构造 soft_next_state(a_i)
6. 计算 future_score(a_i)
7. 合并 HPN logit 和 future_score
8. 选择 final_logit 最大的 item
9. 等待真实用户反馈
10. 用真实反馈更新线上历史
```

第 5 步不是必经步骤。

如果第一版只做：

```text
HPN top-k
-> predictor 预测每个候选的一步后果
-> rerank
```

则不需要 `soft_next_state(a_i)`。

如果启用：

```text
predicted_reward(a)
+ gamma * V(soft_next_state(a))
```

或显式 `k >= 2`，才需要构造它。

这里的 `soft_next_state(a_i)` 是虚构的未来状态，但它不是 simulator 真实 rollout。区别是：

```text
simulator rollout:
  采样一个具体事件，然后把它当成下一步历史继续走。

soft_next_state:
  用预测分布构造一个期望表示，只用于当前候选打分。
```

它不保存进用户历史，也不会替代下一轮的真实状态。

必须确认：

```text
在线第 t 步的 sigma_t 来自真实状态 s_t。
在线第 t+1 步的 sigma_{t+1} 来自真实反馈更新后的真实状态 s_{t+1}。
sigma_t 本身不会被保存下来当作 s_{t+1}。
```

也就是说，每一步都有独立预测信息用于当前决策；预测信息不是线上状态更新来源。

### 9.3 候选最终分数

基础形式：

```text
future_score(a)
= predicted_reward(a)
+ gamma * V(soft_next_state(a))
- eta * regret_risk(a)
```

如果初版不启用 value head，则退化为：

```text
future_score(a)
= predicted_reward(a)
```

如果初版已经有可靠的 regret head，可以用：

```text
future_score(a)
= predicted_reward(a)
- eta * regret_risk(a)
```

最终分数：

```text
final_logit(a)
= normalize(hpn_logit(a))
+ alpha * normalize(future_score(a))
```

如果后续有可靠的不确定性估计，再加入：

```text
final_logit(a)
= normalize(hpn_logit(a))
+ alpha * normalize(future_score(a))
- beta * normalize(uncertainty(a))
```

这里必须做尺度对齐。`hpn_logit` 是对数概率，`predicted_reward` 是奖励尺度，`regret_risk` 是概率尺度，`uncertainty` 可能是方差或熵，不能直接相加。

### 9.4 `hpn_logit(a)` 怎么来

HPN 是逐层生成 SID token。

对候选 item 的 SID path：

```text
sid(a) = [z_1, z_2, ..., z_L]
```

候选级 HPN 分数可以用：

```text
hpn_logit(a)
= sum_l log p(z_l | context_{l-1})
```

也可以用平均：

```text
hpn_logit(a)
= mean_l log p(z_l | context_{l-1})
```

初版建议使用平均，避免 SID level 数量变化影响分数尺度。

### 9.5 为什么不是 mask

如果某个候选因为历史强负反馈必须禁止，可用 mask。

但本模块不是禁止候选，而是改变排序：

```text
高当前分 + 高未来风险 -> 降权
中当前分 + 高未来价值 -> 升权
```

这属于预测后果参与最终决策。

## 10. k=2 前瞻设计

### 10.1 k=2 的实现策略

完整代码保留显式 `k=2` 所需接口，但本机默认不直接展开大规模 `K1 * K2`。

显式 k=2 流程：

```text
对第一步候选 a 预测 soft_next_state(a)
在 soft_next_state(a) 上再跑 HPN 得到第二步候选 b
再对 b 预测未来后果
再取 max_b
```

复杂度大约是：

```text
O(B * K1 * K2)
```

如果 `K1=50`，`K2=50`，每个用户就要预测 2500 个候选路径，推理成本很高。

### 10.2 本机默认训练方式

本机默认先跑：

```text
one-step candidate consequence reranking
```

也就是：

```text
score(a)
= predicted_reward(s_t, a)
```

如果 regret head 已经可靠，可以加入：

```text
score(a)
= predicted_reward(s_t, a)
- eta * regret_risk(s_t, a)
```

这一步不需要 `soft_next_state`。

完整方法中继续保留：

```text
one-step soft update + terminal value
```

也就是：

```text
score(a)
= predicted_reward(s_t, a)
+ gamma * V(soft_next_state(s_t, a))
```

这里 `V` 负责吸收第二步及更远未来价值。

这比显式展开 `k=2` 更稳，也更容易和 HPN top-k 重排结合。

### 10.3 显式 k=2

如果 smoke 和 one-step value 有效，再扩展：

```text
score_2(a)
= r_hat(s_t, a)
+ gamma * max_b [
    r_hat(soft_next_state(a), b)
    + gamma * V(soft_next_state(a, b))
  ]
```

但这需要单独做延迟和稳定性评估。

## 11. 多次采样的保守解释

当前不建议一开始引入复杂多次采样。

如果要对齐 Bellman-Jensen 的：

```text
E_sigma max_a [...]
```

可以有三种实现：

1. 使用 dropout 多次前向，得到多个预测场景。
2. 使用多个 predictor 组成 ensemble。
3. 在输出概率上加入校准噪声，生成多个 `sigma`。

每个 `sigma_m` 必须覆盖同一个候选集：

```text
sigma_m(C_t) = {sigma_m(a_1), ..., sigma_m(a_K)}
```

然后：

```text
target or score
= average_m [
    max_a score_m(a)
  ]
```

注意：

```text
不是给每个 item 单独采样一次响应，然后谁采样好运就选谁。
```

初版建议先做确定性预测：

```text
M = 1
```

等主流程稳定后，再加入采样或 ensemble。

## 12. 训练目标组合

### 12.1 predictor 监督损失

```text
L_pred
= lambda_event * L_event
+ lambda_play * L_play
+ lambda_reward * L_reward
+ lambda_regret * L_regret
+ lambda_next * L_next
```

### 12.2 value 损失

日志回报诊断版：

```text
L_value = mse(V(s_t), G_t^k)
```

这只能用于检查数值尺度和训练是否正常，不作为主要方法。

Bellman-style 主版本：

```text
L_value = mse(V(s_t), stop_grad(target_V(s_t)))
```

### 12.3 reranker 训练损失

初版可以先不训练 reranker，只用公式：

```text
final_logit = hpn_logit + alpha * future_score
```

后续如果训练 reranker，可选：

```text
L_rank:
  正负候选 pairwise ranking loss

L_bce:
  预测当前候选是否正反馈

L_reward:
  final score 拟合 reward
```

但需要注意：

```text
如果 reranker 只拟合当前 reward，它可能又退化成短期点击模型。
```

## 13. 与 RRCA / RAPI 的关系

当前 Like to Unlike 方案已有：

```text
RRCA:
  把 delayed regret 追溯修正到原决策点

RAPI:
  用失败 semantic path memory 对 HPN logits 做软干预
```

future-aware predictor 不应替代 RRCA/RAPI，而应形成第三个模块：

```text
RRCA:
  训练时修正历史 credit

RAPI:
  推理时规避近期失败 semantic path

Future Predictor:
  推理时预测候选物品未来后果
```

三者关系：

```text
RRCA 是后验归因
RAPI 是历史失败记忆干预
Future Predictor 是前瞻后果估计
```

## 14. 分类定位

如果只做：

```text
HPN top-k + predictor 重排
```

更准确的分类是：

```text
prediction-augmented sequential recommendation
```

或：

```text
look-ahead reranking for RL-based recommendation
```

如果训练：

```text
V_Bayes(s)
target = E_sigma max_a [...]
```

才更接近：

```text
Bellman-Jensen style prediction-aware value learning
```

如果继续使用：

```text
learned simulator rollout + actor-critic
```

那整体仍属于：

```text
model-based offline RL
```

原因：

```text
模型 = 学出来的环境响应模型 / 状态转移模型 / reward 模型
不是 actor 或 critic 本身
```

A2C 是优化框架，本身不决定是否有模型。

```text
真实环境 rollout + A2C:
  model-free actor-critic

learned simulator rollout + A2C:
  model-based actor-critic
```

### 17.1 第一步：只做数据审计

产物：

### 17.2 第二步：确定 predictor 输出字段

已经确定：

```text
response_probs 是否只包含五类原始反馈事件
```

要求：


